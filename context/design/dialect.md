# The dialect interface

`database.Dialect` is the interface a provider implements so the base can generate SQL and classify
errors without knowing the engine. It has three methods: `Name` returns the engine's name,
`Placeholder` renders the bind placeholder for the nth parameter, and `MapError` classifies a driver
error.

## It grows by engine difference

The interface gains a method when the base needs to emit or interpret something engines do
differently from the standard, and not before. The placeholder is the first such difference: Postgres
writes `$1`, SQL Server `@p1`, SQLite `?`. Others follow as the base's SQL generation widens — how an
engine returns the rows a write affected (`RETURNING` against `OUTPUT`), how it quotes an identifier,
how it spells a type — and each earns its method when a provider is built for an engine that needs
it, not when it is anticipated.

SQL the standard already fixes is generated by the base and earns no method. Paging is the worked
case: the base emits the SQL:2008 form `OFFSET n ROWS FETCH NEXT m ROWS ONLY`, which Postgres, SQL
Server, Oracle, and DB2 accept, so `Dialect` carries no paging method; one arrives when a provider
is built for an engine that lacks the standard form, as SQLite and MySQL do.

## Error mapping

`MapError` is where a provider translates its driver's errors into the base sentinels, wrapping
both in the dual form `fmt.Errorf("%w: %w", sentinel, err)` (`tiers.md`). It returns the error
unchanged today; classifying constraint violations — unique, foreign-key, check, not-null — into
sentinels arrives with the write path (`../concepts/writes.md`). The sentinels are declared in
the base so that a consumer matches them with `errors.Is` without importing a provider, and an
error no sentinel covers still reaches the caller through the wrap.
